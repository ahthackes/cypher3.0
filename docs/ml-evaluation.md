# ML evaluation plan

This is the plan for Phase 3's evaluation work — the part that needs
real data and your own lab, which can't be done inside this chat. It's
written now so the FYP report has a clear methodology section from day
one, instead of being reverse-engineered after the fact.

## Why Isolation Forest is the default, and the autoencoder is optional

Isolation Forest needs no GPU, trains in well under a second on a few
thousand samples, and has one real hyperparameter to tune
(`contamination` — your estimate of what fraction of training data is
already anomalous). That fits the "i5 6th gen, 8GB RAM, ≤15% CPU"
non-functional requirement with room to spare.

A sequence autoencoder (the proposal's original choice) is the right
tool for catching anomalies that only show up as unusual *order* or
*timing* of events, not just unusual feature values at a single point in
time. `detect/ml/autoencoder.py` ships a PCA-based reconstruction-error
model with the same `fit(X) / score(x)` interface so a real Keras/
PyTorch model can be dropped in later without touching the rest of the
pipeline — see that file's docstring. It's off by default
(`ml.autoencoder_enabled = false`) until it's been evaluated against a
labeled dataset, per the methodology below.

## Datasets

1. **Synthetic baseline** (`scripts/generate_normal_traffic.py`) — fast
   to generate, useful for smoke-testing the pipeline (this is what the
   49 automated tests and the quickstart demo use), but NOT sufficient
   evidence for the FYP evaluation chapter on its own, since it's
   generated by the same assumptions the detector is tested against.
2. **Public labeled data** — LogHub's SSH/auth log datasets are the
   recommended source for a real precision/recall evaluation; they
   include both normal and attack-labeled sequences.
3. **Your own lab** — a VM running Cypher with `general.mode = "active"`
   turned OFF (keep it in `dry_run` for evaluation) and a second
   "attacker" VM (Kali or similar) running `hydra`, `nmap`, `nikto`,
   against services YOU own, generates ground-truth-labeled attack
   traffic alongside real benign traffic from your own normal usage.

## Metrics to report

- **Precision / recall / F1** at each severity threshold
  (`detect.thresholds` in `cypher.toml`), not just at the default cut.
- **False positives per day** under normal (non-attack) usage — this is
  the number that determines whether `active` mode is actually usable,
  not just accurate on paper.
- **Detection latency**: time from the log line being written to the
  alert appearing (use `scripts/benchmark.py` as the processing-time
  component; add wall-clock measurement of the full tail-to-alert path
  in the lab).
- **Isolation Forest vs. rules-only vs. fused**: run the same labeled
  dataset through each configuration (temporarily set
  `score_weight_ml = 0` or `score_weight_rules = 0` in the config) to
  show fusion's actual contribution, not just assert it.

## A known, honest limitation

Isolation Forest and the rule thresholds were tuned by hand against
synthetic data, not a large labeled corpus. Expect to iterate
`isolation_forest_contamination` and the rule `count_threshold`/
`window_seconds` values once real evaluation data is available — report
the before/after numbers in the FYP writeup rather than only the final
tuned result; that iteration is itself evidence of a real evaluation
process to your supervisor.
