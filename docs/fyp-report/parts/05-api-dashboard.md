# Part 5 — API and dashboard

## Files covered

`src/cypher/api/auth.py`, `src/cypher/api/schemas.py`,
`src/cypher/api/app.py`, `src/cypher/api/ws.py`,
`src/cypher/api/routes/{events,alerts,blocks,models,health}.py`,
`web/index.html`, `web/vendor/chart.umd.min.js`

## Purpose

Implements FR-6 (real-time dashboard showing metrics, active blocks,
system health) and the "actionable visualization" module from the
original proposal, served by an unprivileged FastAPI backend — see
`docs/architecture.md` for why it's unprivileged.

## How it works

**`auth.py`** implements single-admin, local authentication. The admin
password is never stored in a config file or the repo — only a bcrypt
hash, set via the `CYPHER_ADMIN_PASSWORD_HASH` environment variable
(generated by `scripts/set_admin_password.py`). Password hashing uses
the `bcrypt` package directly rather than `passlib`'s `CryptContext`:
during development, `passlib` 1.7.x was found to break against
`bcrypt`>=4.1 (`passlib` probes an internal `bcrypt.__about__` attribute
that newer `bcrypt` versions removed) — calling `bcrypt.hashpw`/
`checkpw` directly avoids that whole compatibility surface. Sessions
are a signed, time-limited cookie (`itsdangerous`'s
`URLSafeTimedSerializer`) rather than a server-side session store —
appropriate for a single-admin local tool, and it keeps the
unprivileged API process stateless between restarts. `require_login()`
is a FastAPI dependency injected into every protected route; it raises
401 if the cookie is missing, invalid, or expired.

**`schemas.py`** defines Pydantic request/response models, kept
deliberately separate from `cypher.models`'s internal dataclasses — the
wire format (what the dashboard receives as JSON) can evolve
independently of the internal pipeline representation.

**`app.py`'s `create_app()`** is the FastAPI application factory. It
wires up `app.state.settings` and `app.state.db` (read by every route),
mounts all five route modules plus the WebSocket router, and defines
`/api/login`/`/api/logout` inline. It serves the dashboard itself: `/`
returns `web/index.html`, and `/static/` is mounted to the whole `web/`
directory (which is how the vendored Chart.js at
`/static/vendor/chart.umd.min.js` is reachable).

**Routes** (`events.py`, `alerts.py`, `blocks.py`, `models.py`,
`health.py`) are thin — each queries `request.app.state.db` and maps
SQLite rows to the Pydantic response schemas. `blocks.py`'s
`manual_block`/`manual_unblock` are the only routes that have a side
effect: they construct a `ResponderClient` and forward the request to
the responder daemon, with the logged-in username passed as `actor` so
the audit log distinguishes system auto-blocks from administrator
manual actions. `health.py` exposes both an unauthenticated `/healthz`
(for systemd/monitoring liveness checks) and an authenticated
`/api/health` (for the dashboard's own status display).

**`ws.py`** streams new alerts to the dashboard over a WebSocket by
polling the database every second and diffing against the last-seen
alert ID — a deliberately simple poll-and-diff rather than a real
pub/sub bus, appropriate for a single-admin local tool where the
complexity of a message broker isn't justified.

**`web/index.html`** is a single self-contained page: a login screen,
then a three-panel layout (live alert feed, a severity-breakdown bar
chart, an active-blocks table with per-row unblock buttons). Design
choices made deliberately for this subject matter rather than generic
defaults: a dark, muted navy palette (not pure black) with a
desaturated accent, monospace type for all data (IPs, timestamps, log
explanations) since the content genuinely is log/terminal data, and a
severity color ramp (blue → amber → orange → red) used consistently
across the feed and the chart rather than as decoration. Chart.js is
vendored locally (`web/vendor/chart.umd.min.js`, fetched via `npm
install chart.js` during the build and copied out of `node_modules`,
not left as a CDN `<script src>`) so the dashboard has no runtime
dependency on internet access — consistent with NFR-3 (100% offline).

## Security considerations

- The API never executes firewall commands directly — every block/
  unblock request goes through `ResponderClient` to the privileged
  daemon, which independently re-validates it (see Part 4).
- Session cookies are `httponly` (not readable by page JavaScript, so a
  XSS bug can't trivially exfiltrate the session) and `samesite="lax"`.
  `secure=False` is set explicitly with a code comment to flip to `True`
  once the dashboard is served over HTTPS/behind a reverse proxy — left
  as a known, documented gap rather than a silent one, since this is a
  localhost-by-default tool (`api.host = "127.0.0.1"` in `cypher.toml`).
- No admin credentials or secrets are hardcoded or committed — both are
  environment variables, with the systemd unit's placeholder values
  (`change-me-see-docs`) making it obvious they must be set before
  deployment.

## Testing

Verified via FastAPI's `TestClient` against the real app factory, the
real SQLite database (populated by the `cypher replay`/`cypher train`
demo flow), and real bcrypt hashing: unauthenticated requests to
`/api/alerts` correctly return 401; `/healthz` returns 200
unauthenticated; login with a wrong password returns 401, with the
correct password returns 200 and sets the session cookie; subsequent
authenticated requests to `/api/alerts`, `/api/health`, and
`/api/blocks` all succeed and return real data from the trained model
and replayed demo logs; `/` returns the dashboard HTML; the vendored
Chart.js file is served correctly from `/static/`. These checks are automated in `tests/unit/test_api.py`
(7 tests) — see `parts/06-testing.md`.
